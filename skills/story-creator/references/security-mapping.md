# Security Mapping Reference

## STRIDE Threat Categories

Apply STRIDE to each story that involves data flows across trust boundaries.

| Category | What it covers | Story question |
|---|---|---|
| Spoofing | Identity verification, authentication | "How does the system verify who's making this request?" |
| Tampering | Data integrity in transit and at rest | "Can an attacker modify the data this story processes?" |
| Repudiation | Audit trails, non-repudiation | "Is there an audit record of this action?" |
| Information Disclosure | Data exposure, confidentiality | "What sensitive data flows here — could it leak?" |
| Denial of Service | Resource exhaustion, availability | "Can this be flooded or starved of resources?" |
| Elevation of Privilege | Authorization boundaries | "Can the actor do more than it should be able to?" |

Not every story touches every category. Stories that don't cross trust boundaries and don't handle sensitive data may have N/A for most categories.

**Heuristic for when STRIDE applies:** If the story involves external inputs, network calls, authentication, persistent writes, or secrets — all six categories need an answer.

## SLSA Build Track

Map stories to SLSA levels when they involve artifact production, CI/CD pipelines, or build systems.

**Level 1** — Provenance exists
- Acceptance criterion: "The system generates a signed SLSA provenance document for each build artifact."

**Level 2** — Hosted builds with signed provenance
- Acceptance criterion: "Builds run on a hosted CI platform. The provenance document is cryptographically signed and includes the build platform identity."

**Level 3** — Hardened isolated builds
- Acceptance criterion: "Builds run in an ephemeral, isolated environment. Provenance is generated by the build platform, not by user-controlled scripts. Provenance signing key is inaccessible to build steps."

## OWASP SCVS Controls (abbreviated)

Reference these when stories involve dependency management or software composition:

| Control ID | Area | Description |
|---|---|---|
| BOM-1 | SBOM Generation | Software inventory exists for all components |
| BOM-3 | SBOM Completeness | SBOM includes all transitive dependencies |
| CA-1 | Component Analysis | Automated vulnerability scanning runs on each build |
| CA-2 | Continuous Analysis | Scanning runs continuously, not just at build time |
| PM-1 | Package Manager | Lockfiles present and committed for all dependencies |
| PM-3 | Package Integrity | Package hashes verified on install |

## Evil User Story Inversion

For every data flow story, write the "evil" version first, then invert it into a security requirement:

```
Evil: "As a malicious insider, I want to inject false findings into the audit graph,
       so I can hide real vulnerabilities."

Inverted: "All graph writes SHALL be authenticated, authorized, and include
           tamper-evident audit trails. Unauthenticated write attempts SHALL be
           logged with the requestor's identity and rejected."
```

This pattern reliably surfaces security requirements that pure feature-thinking misses.

## ZeroMQ Security (agent-to-agent stories)

When stories involve ZeroMQ messaging between agents:

- All sockets must use CURVE authentication (not NULL or PLAIN)
- Each agent has unique long-term key pairs
- Test: verify NULL mechanism connections are rejected
- EARS constraint: "The <Agent> shall reject ZeroMQ connections that don't present valid CURVE credentials."

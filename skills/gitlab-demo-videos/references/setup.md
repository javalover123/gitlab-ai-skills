# Setup reference

`scripts/setup.sh <target-dir> [--gitlab-tag <tag>]` restores a working kit. Every step checks whether it is already done, so
re-run it after any failure and it only does the missing work.

## Requirements

| Tool | Version | Notes |
|---|---|---|
| git | 2.30+ | sparse, blobless clone of `gitlab-org/gitlab` over HTTPS |
| Node.js + npm | 20.11+ (22 tested) | Vite build and the Playwright harness |
| Python | 3.10+ with `venv` | Kokoro TTS and the narration step |
| curl | any | model downloads |
| Playwright + Chromium | 1.56 tested | see below |
| ffmpeg | 6+ | system `ffmpeg` if present, otherwise a static build from the `imageio-ffmpeg` wheel |
| Disk | 2 GB free is comfortable | `gl-src` is about 220 MB; `node_modules`, compiled CSS and the Kokoro model add several hundred MB |

`jq` is handy for the verify step but optional.

## What setup.sh does

1. Copies `kit/` (harness, page shell, demos, narration scripts) into the target dir. Files that already exist
   there are kept, so local edits survive a re-run.
2. Finds Playwright: `PLAYWRIGHT_NODE_ROOT`, then the global npm root, then `tools/playwright`. If none has it,
   it installs Playwright into `tools/playwright` and runs `npx playwright install chromium`. Set
   `SKIP_BROWSER_INSTALL=1` when browsers are managed for you.
3. Clones `gitlab-org/gitlab` at the tag in `gl-src.pin` (default `v19.4.1-ee`, or the `--gitlab-tag` you pass)
   with `--filter=blob:none --depth 1` and a non-cone sparse checkout from `kit/gl-src.sparse-checkout`.
4. `npm install --legacy-peer-deps` in `app/`. `kit/app/package.json` pins the exact versions the demos were
   built with (`@gitlab/ui` and `@gitlab/svgs` match GitLab's own `package.json` at that tag).
5. Copies icons, fonts and illustrations from `node_modules` and `gl-src`, then compiles GitLab's CSS with
   `npm run css` (3-5 min; the `graphql_explorer` and `terminal` bundles failing is expected).
   `FORCE_CSS=1` rebuilds it.
6. Links `tools/ffmpeg`: the system binary when there is one, otherwise the `imageio-ffmpeg` wheel's binary.
7. Runs `narration/setup.sh`: a Python venv with `kokoro-onnx` and `soundfile`, the Kokoro model and voices,
   and a copy of the espeak-ng data under `~/.cache/espeak-ng-data`.

Environment knobs: `GL_TAG=<tag>` (same as `--gitlab-tag`), `SKIP_NARRATION=1` (silent videos only),
`KOKORO_MODEL=int8` (92 MB quantized model instead of the 326 MB full one), `WITH_PIPER=1` (adds the Piper fallback
voice), `FORCE_CSS=1`.

## Model and voice downloads

Kokoro-82M (Apache-2.0) runs on CPU through `kokoro-onnx` (MIT). The files come from the
[kokoro-onnx GitHub release](https://github.com/thewh1teagle/kokoro-onnx/releases/tag/model-files-v1.0):

- `kokoro-v1.0.onnx` (full precision, default) or `kokoro-v1.0.int8.onnx` (quantized, smaller and close in
  quality)
- `voices-v1.0.bin` (all 54 voices)

Nothing is committed to this repo: no models, fonts, compiled CSS, screenshots or sample videos. They are all
downloaded or generated by `setup.sh`.

## Where it runs

**Claude Code on the web, cloud sessions and Slack-triggered sessions.** Playwright and Chromium are usually
preinstalled, so setup finds the global install and skips the browser download. The container is thrown away
when the session ends, so run setup at the start of each session and copy any new demo back into the skill
(see "Keeping changes" in `SKILL.md`). The environment's network policy must allow `gitlab.com`, the npm
registry, PyPI and `github.com` release downloads. Hosts such as `huggingface.co` and public CDNs are often
blocked, which is why the kit takes the Kokoro files from GitHub and pages never load anything from a CDN.

**Local macOS or Linux with Claude Code.** Install Node, Python 3 and git first (for example with Homebrew or
your package manager). Setup installs Playwright's Chromium into its default cache. On Apple Silicon, the
`imageio-ffmpeg` wheel ships an arm64 build; a Homebrew `ffmpeg` also works. Recording is CPU-heavy: close other
heavy work while a video records.

**Windows.** Not tested. Use WSL2 with a Linux distribution.

## Use another GitLab version

The pages are built from GitLab's frontend source at one tag. The default is the tag in `kit/gl-src.pin`
(`v19.4.1-ee`). To pick another, pass a release tag or a branch:

```sh
bash <skill-dir>/scripts/setup.sh <work-dir>/gitlab-18 --gitlab-tag v18.11.2-ee   # or GL_TAG=v18.11.2-ee
bash <skill-dir>/scripts/setup.sh <work-dir>/gitlab-next --gitlab-tag master      # newest, unreleased code
```

- The tag is written to `<work-dir>/gl-src.pin`, so later runs in that folder keep it. Use one work folder per
  version to keep several side by side.
- An existing `gl-src/` switches by fetching only that tag (still shallow and blobless), and the CSS is rebuilt.
  The pinned-commit check is skipped for a tag you pass.
- Titles and captions that use `GITLAB_VERSION` (`app/src/shell/gitlab_version.mjs`) show the new version. It
  reads `gl-src/VERSION`, so `master` shows the upcoming release number.
- Setup warns when GitLab's `@gitlab/ui` or `@gitlab/svgs` differs from `app/package.json`. Match those (and
  `vue` and `@apollo/client`) to GitLab's `package.json` at that tag, delete `app/node_modules`, and re-run.
- Not everything follows the tag. The sidebar, layouts and HAML pieces in `app/src/shell/` are copied from 19.4,
  and so are each demo's mount points, data attributes and mock data shapes. Run `node harness/check.mjs <slug>`,
  fix what it reports, and re-check the narration: labels, paths and defaults change between releases. A screen
  that doesn't exist at that tag can't be built.

### GitLab.com, Self-Managed and Dedicated

All three run the same codebase, so one checkout covers them. A page's `saas` option (default true, false on the
admin panel) sets `gon.dot_com` and the GitLab.com-only parts of the shell. `panel: 'admin'` gives the Admin area
sidebar that Self-Managed and Dedicated administrators see (`shell-smoke` uses it). Dedicated has no screens of
its own: use the admin panel with `saas: false`, and copy any Dedicated-only differences from the Rails helpers
into the page's data attributes. The kit builds the EE (Premium and Ultimate) frontend only.
